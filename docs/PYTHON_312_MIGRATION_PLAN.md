# Переход Pyconlyse на Python 3.12

## Граница работы

Хосты — EVEREST и ELYSIUM2. Цель — перевести основной runtime, web и управляемые Tango device servers на отдельную Conda-среду `pyconlyse312` на обоих хостах с возможностью немедленно вернуть `pyconlyse39`. XP agent на Python 3.4 и отдельные окружения Gamma-spectrometer не входят в переключение. Запуск миграции назначен на 25 сентября 2026, 19:00 Europe/Paris; до этого времени работающие службы и конфигурация запуска не меняются.

## Порядок после команды запуска

1. **Снимок и исходные показатели.** На обоих хостах проверить отсутствие эксперимента и активного сбора данных. Сохранить перечень процессов, заданий Windows, версий пакетов, экспорта Conda, логов запуска, веток Git и текущих значений runtime без секретов. Сохранить копии изменяемых конфигураций и снимок актуального дерева EVEREST, включая нужные незакоммиченные файлы. Не смешивать миграционные правки с продолжающейся web-разработкой и не сбрасывать ветку ELYSIUM2.
2. **Среда рядом со старой.** Создать `pyconlyse312` с последним патч-релизом Python 3.12 на обоих хостах. Не модифицировать `pyconlyse39`. Проверить разрешение зависимостей на Windows. Для Basler установить готовое колесо pypylon с поддержкой Python 3.12 и выбрать точную версию по импорту, эмуляции, API-тестам и работе камеры. Собственную сборку рассматривать только если опубликованные версии не подходят. Зафиксировать версии и lock-файл. Если библиотека прибора не поддерживает 3.12, остановить переключение и сообщить конкретный блокер.
3. **Код и статические проверки.** Обновить только необходимые ограничения Python, зависимости, активные launchers и инструкции установки. Проверить `compileall`, импорты Tango/Qt/Basler/NI/других драйверов и доступность нужных DLL. Код, который зависит от изменённого API, поправить с целевыми тестами.
4. **Программные проверки.** Повторить исходный набор из 69 тестов на 3.12 и пройти применимые unit, web, device-server и startup contract tests с `--deny-network`. Сравнить результат с 3.9; новые ошибки устранить до переключения. Проверки реальных приборов не включать в общий pytest-прогон.
5. **Git и доставка.** Создать проверяемые тематические коммиты Pyconlyse, включая необходимые готовые web-изменения, не добавляя секреты, среды, сборочные артефакты и незавершённые файлы. Опубликовать согласованное состояние репозитория, затем обновить ELYSIUM2 с сохранением его `codex/zaber-vd2`. Проверить точные хеши и diff на каждом хосте до перезапуска. Не делать `reset --hard` и force push.
6. **Оркестрация без воздействия на приборы.** На обоих хостах проверить выбор абсолютного Python в CMD-обёртках, переменные и `PATH`, задания Windows, последовательность Tango Database → Starter → device servers, web startup и журналы. Сначала использовать тестовые заглушки и read-only Tango probes. Проверить, что старые пути `pyconlyse39` не остаются в активных точках запуска.
7. **Контролируемое переключение.** Только если все предыдущие ворота пройдены и нет активного сбора данных: сохранить предыдущие значения, переключить действующие конфигурации на `pyconlyse312`, перезапускать по одному компоненту на EVEREST и ELYSIUM2. После каждого шага проверить процесс, версию интерпретатора, Tango readiness, HTTP/WebSocket и журнал ошибок. Не посылать команды движения, питания, лазера или съёмки без отдельного оператора.
8. **Откат при сбое.** Вернуть сохранённые значения `PYCONLYSE_PYTHON`, `PYCONLYSE_ENV`, web-конфигурацию и изменённые launchers; перезапустить затронутые компоненты на `pyconlyse39`; проверить те же readiness и web probes на каждом хосте. Старую среду не удалять. Если автоматическая проверка не доказывает готовность всех критических сервисов, оставить рабочий runtime на 3.9 и представить готовый 3.12-кандидат с перечнем оставшихся проверок.
